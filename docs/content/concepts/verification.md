# Trusting results

Every chain link and response registered in the plugin registry carries a finite-difference check in the test suite: its analytic gradient is compared against central differences over a sweep of step sizes, and the check fails if the two disagree. The same checker is public for user code: `topokit.testing.assert_gradient_matches` takes a scalar function and a gradient function, and raises `GradientMismatchError` if the gradient doesn't hold up, the same way [Custom chain link](../extend/custom-link.md) and [Custom physics](../extend/custom-physics.md) use it on a new link and a new physics model.

The benchmark suite pins reference designs, compliance, density field, volume fraction, and iteration count, for standard problems (the 2D MBB beam and cantilever per PR, 3D cantilever and Michell nightly) against committed baselines, so a change that silently shifts a design's outcome fails CI rather than shipping unnoticed. The nightly performance gate does the equivalent for cost: it compares wall time, peak memory, and solver iteration counts against a committed baseline and fails on a regression, so a change that makes TopoKit slower or hungrier gets caught the same way a change that makes it wrong does.

`result.converged` is `True` when the design stopped changing: the optimizer's step size (the largest per-element change in the design variable, `result.history["change"]`) dropped below the stage's `tol` before `max_iter` was reached. `result.history["kkt"]` is a first-order KKT optimality residual, one value per iteration; it is reported for inspection, not used to decide convergence, since the design-change tolerance is the cheaper and more robust stopping signal in practice. A result with `converged=False` is not necessarily useless, it ran to `max_iter` without settling, but it is worth checking `history["change"]` and `history["kkt"]` before trusting it as a finished design.
