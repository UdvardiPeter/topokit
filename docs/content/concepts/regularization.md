# Filtering, projection, continuation

A density-based optimizer can drive each element's density independently toward 0 or 1. Left alone, the optimum for the discretized problem is often a checkerboard of solid and void elements: an artifact of how the finite element discretization stiffens that pattern beyond what the physical material would achieve, not a real structural feature, and one whose fine detail changes with mesh resolution instead of converging to a stable shape as the mesh refines. Filtering caps how fine a feature the design can express, which removes both problems at once.

`DensityFilter(radius=1.5)` blurs the raw design variables into the density field the physics sees, correlating each element with its neighbors within a physical `radius`, expressed in the mesh's length units rather than an element count. That radius sets a minimum feature size: features smaller than it are averaged away, so the design stops depending on how many elements happen to fit inside that radius and stabilizes as the mesh refines.

Filtering also leaves genuinely intermediate densities in the field, not just 0s and 1s. `Heaviside(beta=...)` is a smooth tanh projection around a threshold `eta` (default `0.5`) that pushes those intermediate values toward the extremes; the higher `beta`, the closer the projection is to a hard step, so the composed filter-then-project design approaches solid-or-void.

`SIMP(p=3.0)` is the material interpolation that turns density into stiffness scale: modified SIMP, `E = Emin + rho^p (E0 - Emin)`. `p > 1` makes intermediate densities cost more stiffness than they contribute to the objective, so the optimizer is rewarded for pushing each element toward 0 or 1 even before Heaviside sharpens the field further.

Starting an optimization at the final `p` and `beta` throws away the easy part of the problem. At `p=1` (no penalization) and `beta=1` (a near-linear projection) the landscape is closer to convex and gradients stay well-behaved everywhere, so early iterations can explore broadly before committing to a topology. Fixing both at their sharpest values from iteration one instead makes the landscape non-convex from the start, and the optimizer can lock into a poor local optimum before it has had a chance to explore. TopoKit's default schedule, used whenever `Study(problem).run()` is called with no explicit `schedule`, is a continuation built to avoid that: it ramps `p` from 1 to 3 over its first three stages, then holds `p` at 3 while doubling `beta` from 1 through 2, 4, 8, to 16 over four more, each stage warm-started from the design the previous one reached. Pass an explicit `Schedule`, such as `Schedule.single(...)` for one fixed stage, to override it.
